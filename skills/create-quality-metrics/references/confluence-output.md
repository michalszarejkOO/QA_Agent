# Publishing the Confluence dashboard

Load when the user picked Confluence output (Procedure step 5, Confluence branch).
Start from
[assets/confluence-template.html](../assets/confluence-template.html) — it's the HTML
that Atlassian's MCP server takes as a page body (`body.format: "html"`), not a generic
template; fill it in rather than composing the body from scratch. Don't use Confluence
storage XML (`<ac:structured-macro>`): that server renders it as raw text.

## Before writing any page body

Call `getContentFormatGuide` with `toolName` `createConfluencePage` (or
`updateConfluencePage`), through `discover` on the connector authorized for the target
site (see [configure-project/references/connectors.md](../../configure-project/references/connectors.md#atlassian-tool-names)), before authoring or editing the body if you haven't recently this
session — the HTML has real nesting rules (panels can't contain tables, table cells
can contain lists and status lozenges, etc.) that are easy to get wrong from memory,
and a malformed body fails or renders oddly rather than erroring clearly.

## Connector and site

Confirm which Atlassian connector is authorized for the target Confluence site with
`getAccessibleAtlassianResources` before calling anything else — don't assume a
previously-known site-to-connector mapping still holds.

## Create vs. update

- **New page**: create under the parent page/space the user named in step 1. Title it
  clearly, e.g. `<Project> Quality Dashboard — <Sprint/Release>` — ask the user if they
  want a different convention (some teams keep one evergreen page per project instead
  of one per sprint; that changes whether this run creates a new page or updates the
  last one).
- **Update existing page**: fetch the current page body first (`getConfluenceContent`
  with `content_format: "html"` and `detail: "full"`; it also returns the
  `snapshotToken` that `updateConfluenceContent` needs). If the page has sections
  beyond the metrics dashboard (team notes, a changelog, anything not generated by
  this skill), **preserve them**, as fetched: replace only the dashboard section,
  the part between the two anchor macros named `quality-dashboard-start` and
  `quality-dashboard-end` that the template puts at its top and bottom (HTML
  comments don't survive on the page, so they can't mark it). A page made before the
  template had anchors has none: ask the user which headings are the skill's own vs.
  theirs. If it's ambiguous which content is safe to replace, ask the user before
  overwriting anything.

## Filling the template

1. **Header table**: project, release/sprint, platforms, last updated date, data
   sources.
2. **Readiness banner**: a status lozenge (`data-color` `green`/`yellow`/`red`) for
   Ready / Ready with risks / Not ready, inside a `panel-success`/`panel-warning`/
   `panel-error` panel carrying the one-sentence reason. Match panel type to
   severity — don't use a success panel for a Not ready verdict.
3. **KPI table**: one row per headline metric — value, trend, target — same 4–6 cap as
   the HTML version; anything beyond that goes in the Details section.
4. **Trend**: if a chart macro is available in this Confluence instance, use it;
   otherwise render the same series as a plain table (period columns, defects-in-sprint
   and escaped-to-production rows) with a one-line note that it's a table rendering of
   the trend, not an image.
5. **Live data over snapshots**: for open critical/high defects (and any other metric
   that's cheap to keep live), embed a **Jira issue macro** with the JQL from
   [data-gathering.md](./data-gathering.md)/[metrics-definitions.md](./metrics-definitions.md)
   instead of a hardcoded count, so the page reflects current state on every view
   rather than going stale between runs. The macro needs only the JQL (`jqlQuery`):
   Confluence uses the Jira site linked to it, no server name or id (checked
   2026-10-27). So the macro only works when the Jira project is on the same
   Atlassian site as the Confluence page; for a project on another site, list the
   issues as links with their count and say on the page when the list was read. Snapshot-only metrics (this sprint's
   regression pass rate, a point-in-time crash-free percentage) stay as plain values —
   only use the macro where "live" is actually more correct than "as of this report."
6. **Feature-area readiness table**: status lozenges (`Ready` green, `Known risk`
   yellow, `Not ready` red, `Not in release` neutral) plus a short note column.
7. **Open risks**: a `warning` panel per risk (or a table if there are many), each with
   impact, likelihood, workaround, plan/owner in plain language.
8. **Details (secondary metrics)**: a `<details>` expand, so it's collapsed by
   default.
9. **Footer**: definitions for the metrics actually used, and the threshold set
   applied (including any override), as plain text — this is what lets a client reader
   understand what the numbers mean without asking.

## Confirm before publishing

Always show the user the assembled verdict, KPI values, and open risks, and ask for
explicit confirmation before calling `createConfluenceContent` or
`updateConfluenceContent` — never publish on the first pass without that check, even if
the request sounded like it wanted the page immediately. After publishing, share the
resulting page link back to the user.
